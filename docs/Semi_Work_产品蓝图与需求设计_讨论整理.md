## 0. 执行摘要

**一句话定位（建议表述）：**

> **Semi Work 是一个以 Agent 驱动、以 Task 为中心的 AI Native 工作协作平台：自动汇聚项目上下文，让人、云端 Agent、本地 Agent、Agent Team 与业务 Harness 围绕共同目标平等协作，持续推进任务直至成果交付。**

产品要解决的不是“个人使用 AI 更快”，而是“**整个团队如何与 Agent 一起把工作做完**”。任务不只是看板中的一条记录，而是一个具有生命周期、上下文、参与者、执行过程、人工决策与产物的**持续性协作空间**。

### 已形成的核心共识

1. **【已讨论确认】以项目空间组织协作**：空间里配置人、Agent、Team、小队及可访问的知识和工具资源。
2. **【已讨论确认】以 Task 驱动工作**：从任务创建到完成，有状态、有协作、有结果，复杂任务可持续数小时到数天。
3. **【已讨论确认】执行机制可变**：单 Agent、通用协作 Team、Matrix AgentTeams，以及业务自定义 Harness 都可以承担任务执行。
4. **【已讨论确认】允许人工持续介入**：需要人确认时，可在任务内 @ 指定人员；参与者共享任务进展，而不只是共享对话消息。
5. **【已讨论确认】执行者“可手选、可自动”**：用户可指定 Agent / Team / Harness；如果未指定，由平台智能判断。BPA 类业务优先验证简洁入口。
6. **【已讨论确认】工作过程展示有深浅之别**：BPA 重结果，产研重阶段、证据、门禁及回退；用一个 Task 底座承载不同的执行视图。
7. **【已讨论确认】支持云端 Agent 与本地 Agent 协作**：这是产品目标之一，不局限于云端运行环境。
8. **【已讨论确认】协作强调“平等协作”**：人与 Agent 不只是“人发令、Agent 回复”，而是共同参与任务推进、决策、执行与交付。

## 1. 背景与问题定义

### 1.1 需求来源

两个业务方提出了相似的“项目空间 → Task → 指派 Agent / Team → 协作执行 → 交付结果”需求，但工作性质不同。

**场景 A：AI Native 产研协作**

- Project 中有不同需求、缺陷、版本等工作对象。
- Task 可能对应一个需求或 Bug；需要状态和可视化看板。
- 背后可能由 **Semi-loop / 业务 Harness** 组织 N1–N5 等专业阶段。
- Agent 根据项目知识库、代码仓库、历史信息理解任务，必要时寻求产品、研发、测试等角色确认。
- 执行可能在云端 Workspace / Sandbox 中拉代码、拆任务、修改、测试、交付。
- 阶段有条件回退，如 N2 回到 N1；需要保留完整过程和阶段性产物。
- 有版本、发布等产研特有的领域模型，但不应强加给全部业务空间。

**场景 B：BPA / 数据分析类协作**

- 项目空间预置成员、Agent 与协作小队。
- 用户下达“拉取数据湖数据 → 分析 → 生成结果 → 通过飞书通知或交付”的任务。
- 可能由某个 Agent 理解任务后自主邀请其他 Agent 或人参与。
- 业务用户更重视**任务目标、当前状态、最终交付物和结果通知**，不需要观看极细的中间流程。
- 支持指定执行者，也支持留空并由平台智能选取。

### 1.2 背后的共性问题

传统项目管理平台有 Task，但不会自行推进；普通 Agent 聊天工具能执行，但缺少跨人、跨 Agent 的长期工作组织和共同事实。

由此产生四类断层：

- **任务与执行断层**：在看板里登记任务，真实执行却散落在聊天、脚本或外部 Agent 中。
- **上下文断层**：人需反复向 Agent 解释项目背景、权限范围、历史决定与已有产物。
- **协作断层**：多个人、多个 Agent 各自执行，缺少共同进度、责任、确认和交接。
- **结果断层**：执行过不等于完成；缺少可核验的结果、验收结论和交付留痕。

### 1.3 产品目标与非目标

**产品目标**

1. 把项目中的人、Agent、Team 和资源组织起来。
2. 将一次任务下达转化为可推进、可协作、可审计、可交付的长期工作对象。
3. 在权限允许范围内，自动获取适合任务的上下文。
4. 根据任务智能选择执行者，或遵从用户明确指定的执行者。
5. 支持需要时的人机交接、审批与验收。
6. 提供统一任务事实及灵活的业务执行视图。

**当前不以此为目标【建议】**

- 不首先复制一个完整的 Jira、飞书项目或通用 OA。
- 不首先内建一套适配所有业务的 BPMN / 通用流程编排器。
- 不要求每个 Task 必须运行多 Agent 或 Harness。
- 不要求所有业务展示产研 N1–N5 的细粒度步骤。

## 2. 产品定位与设计原则

### 2.1 产品定义

**Semi Work = 项目工作空间 + 任务协作 + Agent 智能执行**。

它不是“任务管理工具外加聊天框”，也不是“Agent Hub 外加一个看板”，而是以 Task 为统一协作与交付的核心对象，让智能执行成为工作流的一部分。

### 2.2 核心原则

| 原则 | 产品含义 |
|---|---|
| Task-first | 目标、执行、沟通、产物和验收统一挂在 Task 上 |
| Agent-driven | Agent 理解目标、主动获取上下文并推进；必要时向人请求决策 |
| Human-in-the-loop | 人能参与、修正、确认、验收或中止，不被排除在执行之外 |
| 平等协作 | 人、单 Agent、云端/本地 Agent、不同 Team 在共同工作对象上协同 |
| 结果导向、过程可追 | 默认突出结果；需要时可展开阶段、操作、证据和执行轨迹 |
| 执行可插拔 | 平台不把某一业务 Harness 或 Matrix Teams 机制写死 |
| 受权限约束 | 所有上下文读取、任务调用、产物共享服从项目与资源授权 |

## 3. 核心对象模型

### 3.1 总体关系

```text
Semi Work
├─ 个人工作入口【待确认：个人空间边界】
└─ 项目空间 Project Space
   ├─ 人员 / 角色 / 权限
   ├─ Agent / Team / Harness 可用目录
   ├─ 关联资源：知识库、仓库、数据源、工具、连接器等
   ├─ 项目上下文、约定和历史决定
   └─ Task（可含子任务）
      ├─ 目标、交付标准、状态、责任人
      ├─ 执行者：Agent | Team | Matrix AgentTeams | Harness
      ├─ 参与者与协作消息
      ├─ 上下文与决策记录
      ├─ 执行事件 / 阶段视图（按执行机制扩展）
      ├─ 人工确认 / 审批 / 验收
      └─ 产物、结果与证据
```

### 3.2 项目空间 Project Space

**【已讨论确认】** 是协作范围和资源边界：聚合项目成员、Agent、小队、可用知识与业务工具，承载项目下的多个 Task。

**建议字段**：空间 ID、名称、描述、所有者、成员与角色、可用 Agent、可用 Teams、可用 Harness、关联知识库/仓库/数据源、权限策略、审计策略、创建与更新时间。

**【待确认】** 个人空间与项目空间的具体差异：个人任务默认属于哪里、私人任务是否可转成项目任务、跨空间引用怎样授权。此前已讨论到个人空间的方向，但未取得可还原的逐条结论。

### 3.3 Task：最核心的工作对象

**【已讨论确认】Task 不是一次 Agent 请求。**

一个 Task 从未开始持续到完成，可能经历多次 Agent 调用、人工确认、Team 协作和产物更新。一个任务可以对应“研发需求”“缺陷”或“一次分析报送”。

**建议基础字段**：

- 标识：Task ID、所属空间/项目、标题、描述、创建人、时间。
- 目标：期望结果、交付物类型、验收标准、优先级、计划时间。
- 协作：负责人、参与人、指派执行机制、可见范围。
- 进展：统一状态、阻塞原因、下一步行动、最近活动。
- 交付：产物引用、确认与验收记录、执行摘要、证据链接。
- 扩展：业务类型与业务引用（如 requirementId、bugId、releaseId）。

**建议通用生命周期**：

```text
未开始 → 进行中 → 待确认 / 阻塞 → 进行中 → 待验收 → 已完成
                                  └────────────→ 已取消（可选）
```

实际流转应允许按业务规则调整；**“N1–N5”不是通用 Task 状态**。通用状态表达“任务整体怎么样”，Harness 阶段表达“业务流程跑到哪一步”。

### 3.4 执行体类型与区别

| 执行机制 | 定义 | 适用场景 |
|---|---|---|
| 单 Agent | 独立执行任务、可调用工具和资源 | 简单问答、分析、明确的自动化工作 |
| 通用协作 Team / 小队 | 面向任务组织的多角色协作，可按需分工 | BPA、跨角色工作协作 |
| Matrix AgentTeams | 现有基于 Matrix 的 AgentTeams 机制 | 多 Agent 消息协作、群组式交互 |
| 业务 Harness | 带专业阶段、决策规则、门禁和编排策略的协调机制 | AI Native 研发等复杂流程 |

**【已讨论确认】** 通用 Team 与 Matrix AgentTeams 是**两种不同概念**，不能混为一谈。

**【建议】** 将“任务协调者”与“具体执行者”解耦：Harness 或主 Agent 可以负责计划、派发和验收；实际子步骤可以由某个 Agent/Team 执行。这样，一个任务既能“由 Harness 统筹”，也能“由若干执行体协作”。

## 4. 两类典型工作流

### 4.1 BPA：轻量目标式下达，重点看结果

```text
进入项目空间
  → 新建任务（描述目标 + 可选交付标准）
  → [可选] 指定 Agent / Team
  → 未指定则由系统匹配可用执行者
  → 创建 Task 并启动协作
  → 自动拉取有权限的数据 / 工具上下文
  → Agent / Team 执行分析和报送
  → 必要时 @ 人请求确认
  → 生成报表 / 文件 / 通知结果
  → 任务验收与完成
```

**【已讨论确认】** 用户可以自己选执行者；不选则平台自动判断。**不是**强制用户先接受推荐方案再确认，避免额外步骤。

**交互重点**：任务目标、当前状态、谁在处理、需要谁介入、最近关键动态、最终交付物。

### 4.2 产研：专业 Harness 驱动，强调可追溯过程

```text
需求 / 缺陷进入项目空间
  → 形成 Task，关联需求或 Bug
  → 指派 Semi-loop 等专业 Harness
  → 自动收集知识库 / 代码仓库 / 历史决定
  → N1 意图锁定与人工确认
  → N2 生成 - 验证循环，拆分子任务 / 调用开发 Agent
  → N3 交付确认（质量、安全、体验等）
  → N4 部署执行
  → N5 持续反馈
  ↘ 若不满足条件，按业务规则回退到相关阶段
  → 产物、证据、版本/发布信息沉淀在任务中
```

其中 N1–N5 来自此前 Semi-loop 讨论，是**产研专属 Harness 的示例**，不是要求所有业务必须复用的统一过程。

**交互重点**：整体任务状态 + Harness 阶段、质量门禁、人工确认、回退原因、阶段成果与最终交付。

## 5. 核心产品体验

### 5.1 入口：先描述目标，再选择控制程度

**【已讨论确认】两种执行者选择方式并存**：

- **手动指定**：用户选择项目、Agent、通用 Team、Matrix AgentTeams 或 Harness。
- **自动匹配**：用户只填写任务目标和必要信息，执行者不填，系统基于空间资源、授权与任务类型进行匹配。

**【建议】统一任务创建表单**：

1. 所属项目空间（必填）。
2. 任务目标 / 交付要求（必填）。
3. 执行方式（可选，默认“自动匹配”）。
4. 高级设置（可折叠）：验收人、优先级、时间限制、知识或工具范围。

产研空间可配置默认 Harness；BPA 空间优先提供“描述目标即可创建”的轻量入口。

**【待确认】** 自动匹配后是否直接启动、低置信度是否请求用户确认、涉及高权限操作时是否增加审批门禁。推荐将“执行者选择”与“敏感动作审批”分开处理。

### 5.2 Task 工作台：一项工作的一处共同现场

**【已讨论确认】** Task 本身应像独立协作空间。人和 Agent 在这里持续工作，共享同一事实和交付进度。

**【建议】工作台信息结构**：

| 区域 | 关注问题 | 内容 |
|---|---|---|
| 任务概要 | 要做什么？谁负责？ | 目标、状态、负责人、执行者、时间、验收标准 |
| 关键进展 | 到哪一步？卡在哪？ | 当前步骤、下一步行动、阻塞、待确认 |
| 协作消息 | 谁说了什么？ | 人/Agent @、讨论、决定、反馈 |
| 执行过程 | 系统做了什么？ | 关键事件、子任务、工具调用摘要、可展开执行轨迹 |
| 人工待办 | 轮到谁处理？ | 确认、审批、验收请求 |
| 交付与证据 | 交付了什么？ | 文件、报告、代码/PR、链接、通知结果、验收结论 |
| 专业视图 | 业务细节是什么？ | Harness 的 N1–N5 等可插拔阶段面板 |

**关键设计原则**：不能只做无限滚动的聊天记录。聊天是沟通渠道，**Task 的状态、决策、产物与验收必须结构化存在**。

### 5.3 Agent 自动获取上下文

**【已讨论确认】** 任务创建后，Agent 应主动获取与项目和目标相关的上下文，而不是等待人逐条输入。

**建议上下文来源**：

- 项目配置与空间规则；项目知识库、文档。
- 代码仓库、Issue、PR、研发规范。
- 历史 Task、历史决策与相关成果。
- 数据湖、业务系统及结构化数据。
- 飞书/协作工具中授权范围内的讨论、通知与确认记录。

**权限前置**：项目空间可见 ≠ Agent 自动拥有所有资源权限。应基于发起人、执行体身份、资源范围、用途和操作风险做校验，并记录访问来源与关键使用证据。

### 5.4 主动协作与动态组队

**【已讨论确认】** 某些任务由主 Agent 理解目标后，自主决定需要哪些人、Agent 或 Team，并推动工作。也允许创建前就明确指定小队。

**建议能力**：

- 固定 Team：事先定义成员与角色，多任务复用。
- 动态 Team：围绕任务临时招募、组合和释放参与者。
- @ 人：请求确认、补充信息、批准操作或验收。
- @ Agent：直接委派分析、开发、研究、文档等子任务。
- 人工接管：必要时人工修改目标、重派任务或停止执行。

**【建议】初期可以先支持固定团队与显式邀请，动态自主组队逐步放开**；需要特别设计权限、成本、并发、责任归属和参与者通知。

### 5.5 云端 Agent 与本地 Agent 协作

**【已讨论确认】** 产品希望支持云端与本地 Agent 在同一 Task 上协作。例如云端协调与数据分析，本地开发 Agent 处理开发机代码或本地工作区。

**【待确认】** 本地 Agent 的身份认证、运行状态同步、可用性、网络连接、数据出入边界以及交付产物回传协议。技术上可与既有 Agent OS / A2A 能力结合设计，但不预设具体连接实现。

## 6. 与 Agent OS、Agent Runtime、Harness 的边界

### 6.1 建议的职责划分

```text
Semi Work（协作产品层）
  空间 / Task / 成员 / 协作 / 人工待办 / 任务进度 / 交付 / 产品体验
                  │
             执行请求 / 事件 / 产物
                  ▼
执行协调层（可插拔）
  主 Agent / 通用 Team / Matrix AgentTeams / 业务 Harness
                  │
                  ▼
Agent OS / Runtime（平台能力层）
  Agent Registry / Sessions / Memory / Files / Knowledge / SkillsHub
  ToolsHub / MCP / Sandbox / 权限 / AI Gateway / 可观测 / Hooks
```

**【讨论方向】** Semi Work 应充分复用已有 Agent OS 能力，不重复造 Runtime、Sandbox、记忆、工具注册和模型网关。

### 6.2 任务状态与运行状态不要混淆

一个 Task 可能包含若干次执行运行；一次执行成功不代表 Task 已验收，一个运行失败也不代表整个 Task 应立即关闭。

**【建议】** 保持不同层级：

- **Task 生命周期**：业务工作是否已完成。
- **Execution / Run**：某次执行的状态、开始结束、错误与重试。
- **Harness Phase**：专业业务阶段及门禁、回退逻辑。
- **Human Action**：人工待确认、审批、验收事项。

### 6.3 协作事实与事件

**【建议】** 用结构化的事件沉淀执行与协作：TaskCreated、ExecutorSelected、ExecutionStarted、SubtaskCreated、HumanInputRequested、DecisionRecorded、ArtifactProduced、StageChanged、TaskBlocked、AcceptanceApproved、TaskCompleted 等。

关键人工决定应保留：提出者、确认者、发生时间、依据、适用范围，以及是否被撤销或替代。这样既能渲染工作台，也能承载通知、可观测与审计。

## 7. MVP 产品范围与实现顺序

### 7.1 第一版 MVP（已做交互原型，尚非完整业务系统）

**【建议范围】**

1. 项目空间及空间成员配置。
2. 可使用的 Agent、Team、Harness 目录和绑定。
3. Task 创建：目标、交付标准、手动选择或自动匹配入口。
4. Task 看板：未开始、进行中、待确认/待验收、完成等状态。
5. Task 工作台：概要、动态、协作消息、人工确认、产物列表。
6. 一条真实 BPA 任务链路作为最早验证闭环。
7. 任务状态与执行事件的基本留痕。

**原型现状（2026-11-02）**：已生成 `semi_workspace_mvp.html` 作为**本地单文件可交互概念原型**；具备空间、看板、创建 Task、执行者选择、任务内消息与模拟执行。此原型的“自动匹配”“执行过程”“人工确认”仍为演示交互，**不等于已接入生产 Runtime、权限、持久化与业务系统**。

### 7.2 不应在 MVP 初期强推的范围【建议】

- 通用可视化流程编排器；
- 全场景任意 Harness 配置；
- 完整的版本/发布领域模型；
- 完全自主、无限制的动态 Team 组建；
- 全量跨组织共享和复杂多级审计报表。

### 7.3 推进路径【建议】

| 阶段 | 建设重点 | 能检验什么 |
|---|---|---|
| P0：交互验证 | 项目空间 + Task 创建 + 看板 + 工作台 | 用户是否理解“Task = 协作空间” |
| P1：BPA 真闭环 | Agent/Team 绑定、数据读取、产物、通知、人工确认 | 能否从任务下达走到真实交付 |
| P2：专业 Harness 接入 | 产研 N1–N5、门禁、回退、阶段视图 | 通用 Task 是否能支撑复杂专业流程 |
| P3：自组织协作 | 动态组队、跨云端/本地 Agent、优化自动匹配 | 多执行体能否可靠、高效协作 |

## 9. 尚需讨论的产品与技术问题

**产品侧【待确认】**

1. **个人空间**：是否与项目空间并列？个人任务怎样转移或共享？
2. **任务层次**：Task / Subtask / Run 的具体交互与父子状态聚合规则是什么？
3. **智能选人**：自动匹配是选单 Agent、固定 Team 还是直接选择 Harness？解释推荐依据到什么程度？
4. **动态邀请**：Agent 邀请人、Agent、Team 时，是否需要确认、如何通知、何时释放？
5. **人工确认**：确认、审批、验收是统一待办吗？超时、驳回和重新执行怎么处理？
6. **结果验收**：由谁声明完成，是否允许自动验收，验收失败如何回退？
7. **任务视图**：看板、任务详情、协作聊天和阶段视图的默认布局如何取舍？
8. **跨任务复用**：项目知识与任务中形成的新决策、成果是否回流知识库或记忆库？

**架构侧【待确认】**

1. Task Service 与 Runtime 的状态边界、执行绑定和回调协议。
2. 长任务的暂停/恢复、重试、超时、幂等与任务版本。
3. 跨云端/本地 Agent 的权限、连接、心跳、产物回传。
4. Agent 动态组队时的资源、费用、并发和能力授权。
5. 多方可见时的脱敏、数据访问、操作审批与审计。
6. Harness 扩展需要暴露的阶段事件、门禁结果和自定义任务面板。

## 10. 用来校验产品价值的一条验收故事

> 我是一个 BPA 项目成员。我进入项目空间，输入“分析本周数据湖中的运营指标并发送总结给项目相关人员”。我可以指定一个分析 Agent/Team，也可以不选。系统在授权范围内匹配执行者、拉取资料、开展分析；遇到口径问题时在 Task 内 @ 我确认。我确认后任务继续。最终我能看到结构化的结果、已发送的通知和证据，并在同一任务空间里完成验收。

**这个故事只有全链路成功，Semi Work 才不只是一个带 Agent 入口的任务看板。**

产研场景的第二条验收故事应进一步验证：一个需求 Task 由 Harness 执行，在 N1 与 N2 之间往返，自动调用研发 Agent，阶段证据可见，最终仍回到同一 Task 完成验收。

## 11. 一句话结论

**Semi Work 管“共同要完成什么、谁参与、做到哪里、最终交付了什么”；Agent OS 管执行所需的基础能力；Agent / Team / Harness 管具体怎么把工作做成。**

真正需要做好的不是“创建一个 Task”，而是让 Task 成为**人和 Agent 持续共同工作的事实中心**。
